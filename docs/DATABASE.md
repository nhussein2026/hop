# Hop Database

Hop stores everything in one SQLite file (`DATABASE_URL`, default `storage/hop.db`), accessed through Node's built-in `node:sqlite` driver and Drizzle ORM. The file is created on first start. WAL mode means you'll also see `-wal` and `-shm` files next to it; copy all three, or use a backup, when moving the database.

## Tables

Table definitions live in `apps/api/src/db/schema/`, one file per area. Matching TypeScript types are in `packages/domain`.

| Area | Tables |
| --- | --- |
| Planning | `tasks`, `habits`, `habit_completions`, `events` |
| Goals | `goals`, `goal_criteria`, `goal_progress`, `milestones` |
| Career | `opportunities`, `opportunity_activities`, `opportunity_prep`, `contacts`, `interactions`, `resumes`, `resume_files` |
| Growth | `skills`, `projects`, `evidence`, `finds` (Radar) |
| University | `terms`, `courses`, `assessments`, `key_dates`, `pins`, `uni_links`, `resources`, `resource_files`, `ideas` |
| Reviews | `weekly_reviews`, `monthly_reviews`, `reflections` |
| App | `settings` (a single row) |
| Auth | `credentials`, `sessions` |

Notes:

- IDs are UUID strings. Timestamps are ISO 8601 UTC strings; date-only fields are `YYYY-MM-DD` in the user's timezone.
- File contents (`resume_files`, `resource_files`) are stored as blobs in the database, so backups are self-contained.
- Values computed from other data (goal health, follow-up due dates, grade standing, habit consistency) are **not** stored; the web app derives them. `goal_progress` stores a daily history so progress over time can be charted.
- `credentials` and `sessions` are never included in backups or restores.

## Migrations

Migrations are SQL files in `db/migrations/<timestamp>_<name>/`, generated by `drizzle-kit`:

| Migration | Adds |
| --- | --- |
| `20261007074606_initial` | Core tables: tasks, goals, habits, events, opportunities, projects, skills, evidence, weekly reviews |
| `20261007074840_auth` | `credentials`, `sessions` |
| `20261008001603_features` | Contacts, interactions, goal criteria and progress history, milestones, opportunity activities and prep, reflections, resumes, settings |
| `20261008122246_resume_files_goal_criteria` | `resume_files`, and converts old free-text success criteria into criteria rows |
| `20261008130045_monthly_reviews` | `monthly_reviews` |
| `20261008135759_university_and_radar` | University tables and Radar `finds` |

The API applies pending migrations **on startup, in one transaction**. If it fails, nothing changes and the API doesn't start. A database created before migrations existed is detected and baselined. A database that has only some of Hop's tables is refused; restore a backup or move the file aside.

### Changing the schema

1. Edit the table in `apps/api/src/db/schema/` and update the matching types in `packages/domain` and schemas in `packages/validation`.
2. Generate a migration:
   ```bash
   yarn workspace @hop/api db:generate --name <short-description>
   ```
3. Read the generated `migration.sql`. Make sure it only does what you intended, especially on table rebuilds.
4. If the table is part of backups, add it to the snapshot schema in `packages/validation/src/backup.ts` and the backup repository, with defaults so older backups still restore.
5. Run `yarn test`. `migrate.test.ts` checks that migrations apply cleanly to a fresh database and to a legacy database.
6. Commit the schema change and migration together.

Other Drizzle commands: `db:migrate` (apply without starting the API) and `db:studio` (browse the data).

## Backup Format

A backup is a JSON file with one array per table (camelCase keys):

```json
{
  "version": 2,
  "exportedAt": "2026-10-09T08:00:00.000Z",
  "goals": [ … ],
  "tasks": [ … ],
  "habitCompletions": [ … ]
}
```

- The same schema (`packages/validation/src/backup.ts`) validates every backup on restore, so a malformed or hand-edited file is rejected before anything changes.
- Version 1 backups from earlier versions of Hop still restore; tables and columns they lack get defaults. Duplicate IDs are rejected.
- File contents are base64-encoded inside the JSON.
- Backups are named `hop-backup-<timestamp>.json` in `BACKUP_DIR`. Safety backups taken before a restore are kept alongside them.
