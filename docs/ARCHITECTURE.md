# Hop Architecture

This document explains how Hop is built today: the pieces, how data moves between them, and the decisions behind them. The product rules live in the [product specification](HOP_PRODUCT_SPEC.md); the directory map is in [hop-structure.md](hop-structure.md).

## Overview

```text
 Laptop · Phone · Tablet
 React + TypeScript PWA  ── service worker (app shell + last-read API data)
          │
          │  HTTPS (e.g. tailscale serve) · JSON · session cookie
          ▼
 Node.js API  (@hop/api, one process, node:http)
   route ─► validation (@hop/validation, Zod) ─► service ─► repository ─► SQLite (node:sqlite + Drizzle)
          │
          └─► built web app served from the same origin (yarn start)
```

Hop is one Node process and one SQLite file. There is no separate web server, queue, cache, or external service. Shared TypeScript types (`@hop/domain`) and request schemas (`@hop/validation`) keep the web app and API in agreement.

## Workspaces

| Workspace | Role |
| --- | --- |
| `apps/api` (`@hop/api`) | HTTP API, authentication, persistence, backups, and serving the built web app. |
| `apps/web` (`web`) | React 19 + Vite single-page PWA. |
| `packages/domain` (`@hop/domain`) | Domain types and constants shared by both apps. No runtime dependencies. |
| `packages/validation` (`@hop/validation`) | Zod schemas for every request body and for backup snapshots. |

The packages are consumed as TypeScript source (`main: ./src/index.ts`); there is no build step for them.

## API

### Request flow

`server.ts` is a single `node:http` handler with explicit routes; there is no framework. Each request goes through the same steps:

1. **Non-`/api` paths** are served from the built web app (`static.ts`), with an `index.html` fallback for the single-page app.
2. **Origin check.** Any non-`GET` request whose `Origin` doesn't match the host is rejected with `403`.
3. **Authentication.** Everything except `/api/health` and `/api/auth/*` requires a valid session cookie.
4. **Validation.** Bodies are read with a 1 MB limit (200 MB for restores) and parsed with a Zod schema from `@hop/validation`. Invalid input returns `400` with field errors.
5. **Service.** Business rules live in `services/`: status transitions, completion timestamps, goal progress from success criteria, opportunity timelines, grade standing, and so on.
6. **Repository.** `repositories/` hold persistence only: Drizzle queries with no business decisions.

Services signal failures with typed errors from `errors.ts` (`InvalidInputError` → `400`, `ConflictError` → `409`, `RequestError` → its own status). Missing records return `404`, and anything unexpected returns `500` without leaking details.

Some simple collections (terms, key dates, pins, links, ideas, finds, resources) share one generic `crudRoutes` helper for list, create, update, and delete.

### Persistence

- SQLite through Node's built-in `node:sqlite` driver and Drizzle ORM. Tables are defined in `apps/api/src/db/schema/`.
- Migrations in `db/migrations/` are generated by `drizzle-kit` and **applied automatically on startup** in one transaction. Databases created before migrations existed are detected and baselined.
- Uploaded files (resumes up to 10 MB, library files up to 20 MB) are stored in the database, so a backup is always a single complete file.

See [DATABASE.md](DATABASE.md) for the table list.

### Backups

On startup and then hourly, the API makes sure today's backup exists in `BACKUP_DIR`, then prunes to the last 7 days plus one per week for 4 weeks. A backup is a versioned JSON snapshot of every data table, validated by the same schema that checks restores. Restores are previewed first, take a safety backup, and replace all data in one transaction. "Test a restore" replays the latest backup into an in-memory database to prove it can be restored.

## Web App

### Shell and routing

- `App.tsx` renders a responsive shell: a sidebar on wide screens (≥ 1100 px), an icon rail on tablets (700–1099 px), and a top bar with bottom tabs on phones (< 700 px). On phones, Career, Goals, Growth, Calendar, and Review sit under **More**.
- Routing is hash-based (`#/today`, `#/goals/<id>`, `#/itu/courses/<id>`), handled in `lib/router.ts`. It needs no server support and survives reloads.
- `screens/` holds one component per screen; `editors/` holds the create and edit dialogs; `components/` holds shared UI (rows, menus, dialogs, icons).

### Data store

`store/HopStore.tsx` loads **all** of Hop's data once at startup (settings first, to fix the timezone, then every collection in parallel) and keeps it in one React context.

Every change goes through `commit()`:

1. The UI shows "Saving…".
2. The API request runs (`store/actions.ts`, `store/uni-actions.ts`).
3. On success, the server's answer is merged into the local data, often with an **Undo** toast.
4. On failure, the local data is left unchanged and the error is shown with **Try again**.

The server is the only source of truth. There is no offline write queue.

### Derived data

Health signals, follow-up timing, habit consistency, deadlines, grade standing, agenda building, and notifications are **computed in the browser** from the loaded data (`lib/rules.ts`, `lib/uni.ts`, `lib/notifications.ts`) rather than stored. This follows the spec's rule of deriving rather than duplicating data. These modules are pure functions and carry most of the web tests.

### PWA and offline

- `public/sw.js` is registered only in production builds.
- The app shell and built assets are cached, so Hop opens offline.
- API reads are network-first, and the last successful response is cached so recently loaded data stays readable offline. Exports, backups, and health checks are never cached.
- Writes are never queued or replayed. Offline changes fail visibly.
- Cached API data is deleted on sign-out and whenever the API answers `401`.

## Time and Dates

Date-only values (`YYYY-MM-DD`) follow the user's configured timezone (**Settings → Profile**), never UTC. Both the API (`settingsService.today()`) and the web app (`lib/dates.ts`) compute "today" in that timezone, and date arithmetic happens at noon UTC so daylight saving never shifts a day. Timestamps are stored as ISO strings in UTC.

## Security

A single password, hashed with scrypt, and server-side sessions with hashed tokens. See [SECURITY.md](SECURITY.md).

## Known Limitations

- **Cross-device freshness:** data loads once per app start, so a device that stays open doesn't see changes made on another device until it reloads.
- **Offline start on a new day:** the habit completion request includes today's date, so the first offline start on a new day misses the cache.
- **Bundle size:** the web app ships as one bundle (~550 KB); screens are not lazy-loaded yet.
- **No calendar sync:** Hop's calendar is internal; there is no ICS feed or external calendar import.
